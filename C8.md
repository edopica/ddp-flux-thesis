
# C8 plan — Correctness battery

The README defines C8 as the **correctness battery**, with completion requiring tests that catch known failure modes and pass either locally or in hardware-enabled CI. That should be interpreted narrowly: C8 must prove distributed-training invariants, not add performance optimizations or merely show that a loss decreases. The project rules already require explicit gradient-scaling semantics, communication outside automatic differentiation, correct optimizer-state handling, and regression evidence for every source change.

## Recommended C8 objective

> Demonstrate that Flux DDP produces mathematically correct and synchronized training updates across MPI and native NCCL, remains safe under uneven and conditional workloads, and fails quickly rather than hanging when a regression occurs.

C8 should finish with three layers of evidence:

| Layer                      | Environment       | Purpose                                            |
| -------------------------- | ----------------- | -------------------------------------------------- |
| Fast correctness suite     | MPI, CPU, 2 ranks | Run on every relevant pull request                 |
| Extended correctness suite | MPI, CPU, 4 ranks | Exercise asymmetric and small-dataset edge cases   |
| Hardware correctness suite | NCCL, 2 CUDA GPUs | Prove that the native GPU communication path works |

The existing C7 example should remain the final end-to-end smoke test, not become the sole proof of correctness.

## Findings that shape the plan

### 1. Reconcile the branch metadata first

Both the main README and the current-context document now correctly report `master`. C8 should proceed on the `master` branch, recording the exact C7 tip.

### 2. There is an uncovered tiny-dataset sharding failure

The current padding implementation at `src/distributed/public_api.jl:273` appends `1:(total_padded - total_size)`. With one sample and four workers, that produces indices equivalent to `[1, 1, 2, 3]`, even though only index `1` exists. The bug only manifests when `pad_count > total_size`. Existing sharding tests cover divisible and non-divisible datasets, but not a dataset smaller than the worker count. This should be the first new fail-first regression test.

The intended behavior should be explicitly selected and documented:

* For `0 < dataset_size < world_size`, cyclically repeat valid samples so every rank receives the same number of elements.
* For an empty dataset, throw a clear `ArgumentError` before distributed execution starts.
* The fix expression (in `public_api.jl`): replace `append!(indices, 1:(total_padded - total_size))` with `append!(indices, [mod1(i, total_size) for i in 1:(total_padded - total_size)])`.

**Boundary verification** — current vs. expected behavior:

| `total_size` | `world_size` | Current `pad` indices | Expected (cyclic mod1) |
| -----------: | -----------: | --------------------- | ---------------------- |
|            1 |            4 | `1, 2, 3`            | `1, 1, 1`             |
|            2 |            4 | `1, 2`               | `1, 2`                |
|            3 |            4 | `1`                   | `1`                   |
|            4 |            4 | *(no pad)*            | *(no pad)*            |
|            7 |            4 | `1`                   | `1`                   |

### 3. The existing "NCCL" tests do not prove native NCCL communication

The distributed common and synchronization tests currently use CPU arrays. In the NCCL extension, host-array operations fall back to MPI; only CUDA arrays on a CUDA distributed device take the NCCL path. Therefore, a test launched with the NCCL backend but operating on `Array` does not prove that NCCL collectives work.

Native NCCL acceptance must require:

* `CuArray` model parameters, gradients, and collective operands.
* `CUDA.allowscalar(false)`.
* At least two visible CUDA devices.
* A logged assertion that the distributed device and data are CUDA-backed.
* `CUDA.synchronize()` after every NCCL collective before reading results, since NCCL kernels are asynchronous.
* An explicit skip or failure when hardware is absent; a host fallback must not be reported as an NCCL pass.

### 4. The optimizer test is too weak to detect missing averaging

The existing optimizer test uses the same all-one gradient on every rank and performs one Adam update. That result is unchanged if the all-reduce is accidentally skipped, because every local gradient is already identical. The management repository's gradient verifier is stronger: it compares averaged DDP gradients and parameters to a deterministic single-process baseline over multiple steps.

C8 should port that invariant into the Flux test suite using rank-dependent data and gradients.

### 5. The unused-parameter unit test proves tree manipulation, not distributed training

The existing unused-parameter test checks the structural gradient-resolution operation on CPU data, but it does not perform a real distributed optimizer update or compare the result with a mathematical baseline. The management verifier already exercises conditional models, actual collectives, updates, and manual expectations; a minimal version of that test should move upstream.

### 6. Deadlocks and CI coverage are not yet controlled strongly enough

The distributed launcher does not currently impose a per-test timeout. In addition, distributed tests are opt-in through environment flags, while the normal CI workflow does not enable those flags. Consequently, an ordinary green CI run is not evidence that the MPI distributed suite executed.

A deeper launcher issue exists beyond the `@test true` on `runtests.jl:28`: child processes using `@test` macros report results to their own local `Test.DefaultTestSet`, which is never communicated back to the parent process. Julia's `run()` checks exit codes, but MPI `mpiexec` exit codes are unreliable and `@test` failures do not guarantee a nonzero exit. The launcher must use one of two mechanisms: (a) each child writes a machine-readable result file (JSON/JLD2) that the parent reads and re-asserts, or (b) each child calls `exit(1)` on any test failure — a pattern already used by `verify_gradients.jl:167` and `verify_conditional.jl:411`.

## C8.1 — Harden the distributed test harness

**Goal:** make failures diagnosable and make hangs terminate predictably.

The launcher should:

1. Run each distributed test file in an isolated process group.
2. **Child-process result propagation** — enforce one of two mechanisms:
   * (a) Each child writes a JSON/JLD2 result file; the parent reads and re-asserts all test results.
   * (b) Each child calls `exit(1)` on any test failure (pattern: `if !any(test_results.passes); exit(1); end`).
   * Option (b) is simpler and already demonstrated by `verify_gradients.jl:167` and `verify_conditional.jl:411`.
   * Put this enforcement in a shared test helper that every distributed test must `include`.
3. Apply a watchdog timeout to every invocation.
4. **Signal-based stack dump on timeout** — before killing the MPI process group, send a signal (e.g., `SIGUSR1` or `kill -USR1`) to force all ranks to dump current stack traces to stderr, identifying which `MPI.Wait` or `NCCL.Allreduce` call is hanging.
5. Kill the complete MPI process group when the timeout expires.
6. Treat a timeout as a failed test, not as an infrastructure skip.
7. Print a concise header containing:

   * Backend.
   * World size.
   * Rank.
   * Device type.
   * Operand array type.
   * Flux commit.
8. Verify that the requested number of ranks was actually started.
9. Sort test files before execution for reproducibility.
10. Distinguish:

    * Unsupported environment.
    * Explicit skip.
    * Test assertion failure.
    * Process crash.
    * Timeout/deadlock.
11. Add a CI-level timeout as a second safety boundary.

A shared helper file (`test/ext_distributed/helper.jl` — without the `_distributedtest` suffix so the launcher doesn't discover it as a test) should hold:

* Deterministic rank-dependent input creation.
* Structure comparisons (`compare_structures`).
* Model-state comparisons.
* Backend/device assertions.
* Rank-dependent seeding: `Random.seed!(base_seed + MPI.Comm_rank(comm))`.
* The child-process exit-code enforcement wrapper.

**Exit condition:** intentionally inserting a deadlock causes a bounded, clearly reported test failure with stack traces identifying the hanging collective.

## C8.2 — Collectives, synchronization, and sharding

### Collective invariants

Use different values on every rank. For example, rank `r` contributes `r + 1`, allowing exact expectations for sum and average.

Cover:

* Broadcast from rank `0`.
* Broadcast from a nonzero root.
* Reduce and all-reduce.
* Sum and average reductions.
* In-place and out-of-place variants where supported.
* `Float32` and `Float64` on MPI.
* `Float16` and `Float32` on NCCL (where supported by the NCCL build).
* `BFloat16` on NCCL (where supported).
* Nested model or optimizer-state structures where supported.

Every average test must use rank-dependent values; identical values cannot prove that communication occurred.

**Explicit sum-vs-average convention test (invariant, not reference-based):**

* With `world_size=2`, rank 0 provides `[2.0]`, rank 1 provides `[4.0]`.
* After all-reduce with `avg`, result must be `[3.0]`.
* After all-reduce with `+`, result must be `[6.0]`.
* This tests the convention directly, independent of any reference computation.

**NCCL vs. MPI average equivalence:** all-reduce the same large `Float32 CuArray` with `NCCL.avg` and with MPI sum+manual division (host copy of the same values), verifying element-wise maximum difference < `1e-6`.

**Buffer reuse safety:** all-reduce with rank-dependent values, verify result, modify the same buffer to different rank-dependent values, all-reduce again, verify the second result is independent of the first (no stale state leakage).

### Structural traversal determinism

Verify that `Functors.fmap` traversal order is identical on all ranks for a nested model with a custom `@functor` type with fields in a specific order. All ranks must produce arrays in the same `collect_arrays` order. Left unchecked, struct field ordering differences can cause MPI message mismatching (garbage values, no error).

### Synchronization invariants

Verify that:

* Rank-dependent initial model values become identical after synchronization.
* Nested Flux model parameters are synchronized.
* Optimizer state is synchronized.
* **Multi-learning-rate optimizer sync**: a model with per-layer `Descent(0.01)` and `Descent(0.001)` preserves hyperparameter assignments, state structure, and values across ranks after synchronization.
* All ranks hold the same parameters after every update, not only at the end.

### Data-sharding invariants

Add deterministic tests for:

| Dataset size | World size | Required behavior                                   |
| -----------: | ---------: | --------------------------------------------------- |
|            8 |          4 | Exact non-overlapping equal shards                  |
|            7 |          4 | Valid cyclic padding and equal local lengths        |
|            2 |          4 | Valid repeated samples only                         |
|            1 |          4 | Every emitted index is `1`                          |
|            0 |          4 | Explicit `ArgumentError` before distributed start   |

Also test:

* Paired data such as `(features, labels)` as tuples **and** named tuples.
* Mismatched-size tuples (assert expected error).
* Equal numbers of local batches.
* The last partial batch.
* A DataLoader integration case with deterministic ordering.
* No rank reaching a collective fewer times than another rank.

**Multi-epoch determinism:** with `shuffle=true`, verify that the pseudo-random generator state is synchronized such that all ranks get mutually exclusive shards of the newly shuffled order across epochs, and that cyclic padding respects the new permutation.

**Synthetic tensor constraint for N < world_size tests:** Use controlled non-zero, non-constant synthetic tensors — not random data. A single repeated sample with a zero gradient will create degenerate Adam state (NaN from second-moment correction `1/(sqrt(v) + epsilon)`).

The first implementation test should be `dataset_size = 1`, `world_size = 4`. After it fails, fix the padding logic by cycling over valid indices rather than appending an unrestricted integer range.

**Exit condition:** all generated indices are valid, all ranks execute the same number of training steps, no uneven-shard case hangs, shuffle determinism holds across epochs.

## C8.3 — End-to-end gradient and optimizer equivalence

**Goal:** prove that DDP updates equal a deterministic single-process global-batch update.

### Loss convention (must be codified before writing tests)

```
Reference (single-process):  loss = sum(losses) / global_batch_size
Each DDP rank:               local_loss = sum(losses_i) / local_batch_size
Distributed gradient avg:     avg = sum(gradients) / world_size
```

This equivalence holds when the loss is linear in the batch dimension (e.g., MSE, cross-entropy with mean reduction). Include one test with a loss function formally provable under this convention and one stress-test with a custom per-sample loss.

### Model and optimizer rules

Use a small model without dropout, batch normalization, or other stochastic/stateful layers. Fixed tensors are preferable to random generation.

For every step:

1. Start all ranks from identical parameters and optimizer state.
2. Give each rank a different local batch (via deterministic fixed tensors).
3. Compute the local mean loss.
4. Compute local gradients.
5. Perform the distributed average.
6. Compare the averaged gradients with a single-process reference gradient computed over the concatenated global batch.
7. Apply the optimizer.
8. Compare:

   * Every model parameter.
   * Every optimizer-state leaf.
   * All ranks against one another.
   * All ranks against the reference implementation.

Run this for:

* `Optimisers.Descent`, which makes scaling errors easy to diagnose.
* `Optimisers.Adam`, which verifies stateful optimizer behavior.
* **Multi-learning-rate optimizer**: a model where layer A uses `Descent(0.01)` and layer B uses `Descent(0.001)`, verifying state structure, hyperparameter assignments, and values.
* At least five consecutive updates.
* Two and four MPI ranks.
* Two NCCL ranks on CUDA.

Use rank-dependent data so these regressions are detected:

* Missing all-reduce.
* Sum used instead of average.
* Accidental double averaging.
* Update performed before communication.
* Optimizer state initialized or advanced differently on different ranks.
* Mixed per-layer learning rates diverging.

A decreasing loss can be recorded for diagnostics, but must not be an assertion of correctness.

### Gradient accumulation invariant (no_sync context)

Verify that when accumulating gradients across micro-batches:

1. Ranks do **not** communicate during the first N−1 micro-batches.
2. The single all-reduce on the Nth micro-batch yields mathematically identical parameters to a single macro-batch forward pass of equivalent size.
3. This is critical because gradient accumulation is the default pattern at scale (memory constraints); the `no_sync` / sync-on-final-step boundary is a common source of DDP bugs.

### Tolerance calibration

MPI `Allreduce` summation order (pairwise, recursive halving) differs from sequential single-process summation. For `Float32`, this can produce discrepancies exceeding `1e-5` on larger tensors.

Calibration procedure:

1. Run the single-process baseline with manual rank-simulated reduction in the **same order** as MPI.
2. Measure the maximum element-wise discrepancy.
3. Set the test tolerance to 10× that measured discrepancy.
4. Document the calibration result and chosen tolerance.

Starting tolerances (subject to calibration):

* MPI `Float64`: begin around `rtol=1e-10`, `atol=1e-12`.
* MPI/CUDA `Float32`: begin around `rtol=1e-5`, `atol=1e-6`.
* `Float16` (NCCL): begin around `rtol=1e-2`, `atol=1e-3`.
* Relax a tolerance only when a documented reduction-order difference justifies it.

Tolerances apply to the **final** step's per-element maximum difference. If per-step checks are used, the effective tolerance at step N should be `N × base_tolerance` (linear accumulation worst-case).

**Exit condition:** gradients, parameters, and optimizer state match the reference after every step; gradient accumulation invariant holds.

## C8.4 — Conditional computation and unused gradients

**Goal:** prove both liveness and mathematical correctness when parameter usage differs by rank.

### Fast two-rank test

Use a model with:

* A shared trunk.
* Head A.
* Head B.

Rank `0` uses head A and rank `1` uses head B. After unused gradients are resolved and averaged:

* Shared parameters receive the average of both rank contributions.
* Head A receives its active contribution divided by the world size.
* Head B receives its active contribution divided by the world size.
* All ranks finish with identical parameters and optimizer state.

### Extended four-rank cases

Cover:

1. A whole layer unused on some ranks.
2. A nested subtree unused.
3. Only one leaf, such as a bias, unused.
4. Different subsets active on each rank.
5. A parameter unused by all ranks — **gradient leaf must be `nothing` and the optimizer state for that parameter must remain frozen** (no update to momentum buffers). Document this in the matrix.
6. All parameters used, confirming the resolver is a no-op in the ordinary case.

### Property-based testing (fuzzing)

In addition to the static cases above, add a property-based test:

* Construct a moderately deep network.
* On each rank, randomly disable gradients for N% of parameters during the forward pass.
* Run the automated verifier logic across thousands of random configurations.
* This catches edge cases that hand-written cases miss and scales test coverage exponentially.

### resolve_unused_parameters! ordering invariants

Add explicit tests for:

1. **Normal ordering**: `resolve_unused_parameters!!` before `Optimisers.update` — should pass and match baseline.
2. **Swapped ordering**: `Optimisers.update` before `resolve_unused_parameters!!` — should either produce identical results or emit a clear error (not silently diverge).
3. **Negative test (missing call)**: With a conditional model, deliberately omit `resolve_unused_parameters!!` and assert the expected failure mode (crash with clear error message, not deadlock or silent divergence). This determines whether the resolve step is a safety net or a mandatory prerequisite.

For every case:

* Perform a real distributed optimizer update.
* Compare against a manually constructed global gradient baseline.
* Run more than one update.
* Keep the watchdog active.
* Check model and optimizer synchronization after every step.

The historical regression set must continue to cover the PMI-environment mismatch, non-divisible sharding deadlock, and unused-gradient deadlock already addressed by the prior work. ([GitHub][1])

**Exit condition:** no conditional case hangs, every resulting update matches the manual reference, the property-based fuzzer finds no divergences, and the missing-call negative test produces a clear diagnostic failure.

## C8.5 — Native NCCL battery

**Goal:** repeat the most important semantic tests through actual NCCL dispatch.

The hardware suite does not need to duplicate every CPU test. It should include the smallest set that proves each critical layer:

1. Native CUDA broadcast and all-reduce with rank-dependent `CuArray` values.
2. `Float16` all-reduce (if supported by the NCCL build).
3. Gradient averaging against a reference.
4. NCCL vs. MPI average equivalence test (from C8.2).
5. Multi-step `Descent` update.
6. Multi-step `Adam` update and state comparison.
7. Gradient accumulation invariant (from C8.3).
8. Conditional two-head model with unused gradients.
9. Model and optimizer-state synchronization.
10. The C7 end-to-end training example as final smoke coverage.

For every NCCL test:

```julia
CUDA.allowscalar(false)          # before model construction
CUDA.synchronize()               # after every NCCL collective before assertions
```

Every test must assert that operands are `CuArray`. A run that silently uses host arrays is an MPI fallback test and must not satisfy the NCCL acceptance criterion.

**Exit condition:** the native two-GPU suite completes without scalar indexing, fallback labeling, divergence, or deadlock.

## C8.6 — CI, reproducible commands, and evidence

### CI layout

**MPI PR job**

* Linux.
* Two MPI ranks.
* Full fast distributed suite.
* Explicitly enable distributed MPI tests via `FLUX_TEST_DISTRIBUTED_MPI=true`.
* Install MPI on the runner (e.g., `apt-get install libopenmpi-dev` or use `MPI.jl`'s `MPI_jll`).

* Four MPI ranks.
* Sharding and asymmetric conditional subset.
* Can run on every relevant pull request if runtime is small; otherwise it must be a required pre-merge command.

* Two GPUs.
* Explicit `FLUX_TEST_DISTRIBUTED_NCCL=true`.
* No CPU-array fallback.
* Run on the available hardware-enabled runner or as a documented acceptance run.

The CI log must visibly list the distributed test files that executed. Merely setting a green workflow status is insufficient evidence.
