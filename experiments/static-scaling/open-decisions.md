## Notes per decision

**OD-1.** The architecture follows the detailed proposal and is fully specified in the spec. The parameter count 11,271,432 was independently recomputed (convolution 11,159,232 + GroupNorm 9,600 + classifier 102,600) and equals the proposal's formula applied to TorchVision ResNet-18. **Recorded 2026-10-16:** GroupNorm-32 and the removed max-pool are confirmed, and the initial-parameter recipe is confirmed (Kaiming-normal `fan_out` with ReLU gain, PyTorch `Linear` defaults for the classifier, GN `gamma = 1`/`beta = 0`). One canonical bundle is generated once with a recorded generator, generator version, and seed, and both frameworks load that same bundle; the bundle hash and recipe are recorded in the Phase 2 fixture manifest.

**OD-2/OD-3.** **Recorded 2026-10-18 (user):** AdamW with `lr = 1e-3`, `wd = 1e-4`, `betas = (0.9, 0.999)`, `eps = 1e-8`; decay applies to the 20 convolution weights and the classifier weight (21 leaves, `lambda = 1e-4`), and no decay applies to the 40 GroupNorm `gamma`/`beta` arrays and the classifier bias (41 leaves, `lambda = 0`). The proposal's original TorchVision recipe (SGD momentum 0.9, lr 0.2, wd 1e-4) does not transfer to AdamW, so these are a new, documented choice; both frameworks use the identical rule. Verified library facts: Optimisers 0.4.9 `AdamW` with the default `couple = true` implements `x = x - eta*(dx + lambda*x)` exactly like `torch.optim.AdamW`; `OptimiserChain(Adam, WeightDecay)` is **not** equivalent and must not be substituted. Weight-decay exclusions follow standard practice and map to `ndim >= 2` on the PyTorch side and to a Functors-compatible rule tree on the Flux side. The Step 4 probe (job `60948431`) asserts the 21/41 membership and the per-leaf `lambda` values in both frameworks.

**OD-4.** **Recorded 2026-10-18 (user):** 5 warm-up epochs and a 50-epoch learning-curve budget, indexed by global update: `W = 975`, `T = 9,750` at batch 512; the batch-256 alternate `W = 1,950`, `T = 19,500` remains available for the Phase 5 batch decision. The schedule is defined by global update index (equations in the spec), not by wall-clock or rank. The published BatchNorm/SGD numbers of the reference recipe are context only and are not acceptance thresholds for GroupNorm/AdamW. The Step 4 probe checks the boundaries at `1`, `W`, `W+1`, and `T`.

**OD-5/OD-6.** The proposal requires "matching preprocessing and augmentation decisions, indexed by sample and epoch rather than rank". The mechanism is fixed now: one saved decision record per (epoch, global sample index), replayed by both frameworks. **Recorded 2026-10-16:** the training transform set is zero-padding of 4 per side, then a uniformly sampled 64x64 crop (zero-based `crop_top`/`crop_left` in `0..8`, sampled independently), then a horizontal flip at probability 0.5; the `(crop_top, crop_left, flip)` triple is saved per (epoch, sample_id). The normalization constants are per-channel RGB population mean and standard deviation computed once from all 100,000 original training images, on the canonical decoded uint8 data scaled to [0,1], before augmentation, padding, and epoch tail dropping, with float64 accumulation; validation and test images are never used. The constants are frozen as float32 values in the fixture manifest and applied identically by both frameworks. A different seed does not produce matching augmentation across frameworks; the saved record does.

**OD-7/OD-8.** The proposal's activation estimates are planning assumptions, not measured limits. The pilot measures forward, backward, communication, guard, and optimizer memory at one, two, and four GPUs, and the margin decides pass/fail. If both candidate batches fail, the experiment requires a documented revision before the campaign.

**OD-9.** JPEG decode once, at preparation time, removes PIL-versus-Julia decoder differences and allows exact decoded-input equality tests. The cost is that the end-to-end view measures augmentation and host-to-device staging but not raw JPEG decode. Both frameworks are treated identically, and the limitation must be stated in the final report.

**OD-10.** Same-framework tolerances stay at the project standard (2e-6 / 1e-5). **Recorded 2026-10-17:** the cross-framework rule keeps the elementwise form `|a - b| <= atol + rtol * max(|a|, |b|)` and the base `atol = 1e-5`, `rtol = 1e-4` for every category except `phase3.grads.u1` (`atol = 1e-3`), `phase3.grads.u3` (`atol = 2e-3`), and `phase3.m.u3` (`atol = 2e-4`); all three overrides keep `rtol = 1e-4`. The basis is the same-framework PyTorch CPU-vs-GPU control on identical generator, fixture, bundle, updates, and provenance: it fails the base rule on exactly these three backward categories at 3.021732e-4 / 14,365 violations, 4.099458e-4 / 128,170, and 5.057361e-5 / 1,137, with the same worst leaves. The four-comparison Flux/PyTorch envelope maxima are 4.126653e-4, 7.480253e-4, and 9.655068e-5, so each new floor has at least 2x margin (2.42x, 2.67x, 2.07x). Per-leaf relative L2 remains supplementary and does not replace the elementwise rule. Evidence: [`artifacts/logs/static-scaling/2026-10-17-phase3-numerics/RESULTS.md`](../../artifacts/logs/static-scaling/2026-10-17-phase3-numerics/RESULTS.md). Any later tolerance change again requires a documented numerical cause.

**OD-11.** **Recorded 2026-10-18 (user):** explicit two-phase training — `Zygote.withgradient` for differentiation, then `Optimisers.update!` on `DistributedOptimizerState`; all communication happens outside AD. The explicit path is the project's established benchmark path (Phase K driver), keeps communication outside AD, and keeps the ADR-0009 gradient guard inside the timed workload. It uses 64 collectives per update: 1 presence allreduce + 62 gradient allreduces + 1 gradient-validity vote. The eager `Flux.train!` path additionally runs the ADR-0008 loss vote (65 collectives) and is not selected.

**OD-12/OD-13.** The phases document requires one fixed update count for timing and a fixed total CPU budget with recorded worker and thread counts. The proposed policy keeps total CPU at 32 cores for every configuration and one compute thread per rank; the pilot and the timing dry run record the effective thread and affinity settings.

**OD-14.** **Recorded 2026-10-19:** [benchmark policy and numerical claims](OD-14-benchmark-acceptance.md). The baseline retains strict FP32, Flux FMA-only selection, deterministic PyTorch cuDNN, and the existing timed guard differences. Claims remain descriptive. Phase 3/4 acceptance stays short-horizon and source-specific. Long-run diagnostics require finite complete state, consistent replicas, and matched work, but apply no trajectory-equivalence threshold. Same-framework and cross-framework discrepancies remain separate. Stronger numerical or training-quality claims require prospective criteria and distinct acceptance evidence. The final Phase 6 cross-framework report requires a deterministic-mode sensitivity in both frameworks. Historical artifacts keep their qualifications.
