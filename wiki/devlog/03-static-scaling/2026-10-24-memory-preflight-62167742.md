**Status: PASS (preflight only).** All nine batch-256 framework/world
configurations are below the OD-8 whole-process sampled peak limit. The
390-update campaign was **not** run. No throughput or memory-over-time result
is reported.

## Allocation change

The user reported that resource usage scales with the CPU core count and asked
for a small allocation because throughput is no longer the goal. The campaign
launcher default and the Slurm submission changed from 32 CPUs to **4 CPUs per
task**. The checker now requires `CAMPAIGN_CPUS = 4` for campaign readiness
instead of 32. Julia ranks use one thread each; PyTorch runs four processes on
four CPUs with one thread each. The 4-CPU timings are not comparable to the
32-CPU campaign and are not used as performance evidence.

At Flux W=1, **91% of the 49.8 GiB peak is already present before the measured
window**; the 20-update increment is only 4.2 GiB. The harness calls `GC.gc()`
before timing but deliberately does **not** call `CUDA.reclaim()`, so
`nvidia-smi` also counts CUDA.jl's cached free blocks from setup and warmup.
The 4.6× process-footprint difference at W=1 is real, but this is not yet a
clean live-tensor comparison of one training step. A reclaim diagnostic is
needed before drawing a framework conclusion.

Every rank had repeated whole-process samples and at least one
training-window sample (5–18 training samples per rank). Actual maximum trace
gaps were 0.29–0.44 s against the 0.25 s target. Samples are `nvidia-smi`
per-process used-memory values, not continuous high-water marks, and include
allocator caches/runtime overhead. The preflight window is 20 warmup + 20
measured updates; the campaign is 20 warmup + 390 updates, so a campaign run
can reach a higher peak. This PASS does not establish that the campaign stays
below 80%.
